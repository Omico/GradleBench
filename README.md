# GradleBench

用 1000 个 Android library 模块，比较 Gradle 7.5.1 与 7.6.6 的构建耗时和内存占用。模块分为 100 组，每组 10 个，共 900 条直接依赖。Java 源码实际引用依赖模块中的类型。

## 测试条件

|项目|固定条件|
|---|---|
|构建工具|AGP 7.4.2，Groovy DSL|
|Java|Zulu JDK 17.0.20.1+1，源码与字节码目标 11|
|Android|compileSdk 33，Build Tools 30.0.3|
|JVM|初始 heap 512 MiB，最大 heap 6144 MiB，G1 GC|
|执行资源|4 workers，关闭并行项目执行|
|缓存|关闭 build cache、configuration cache 和 configuration-on-demand|
|主机|Apple M4 Pro，14 核，64 GiB 内存，macOS 27.0.1|

正式测试串行采用 ABBAABBA 顺序，A 为 7.5.1，B 为 7.6.6。每版每场景测量 4 次，全部成功。依赖下载和两版各自的在线、离线预热不计成绩。正式命令使用离线模式。

## 内存指标

RSS（Resident Set Size，常驻集大小）表示进程当前驻留在物理内存中的内存量。对 Java 进程，它包括 Java heap 中驻留的页面，以及元空间、线程栈、JIT 代码、其他堆外内存和共享库等驻留页面。

RSS 与 Java heap 已用量的统计口径不同。GC 回收对象后，JVM 可能保留内存供后续使用，RSS 因而未必立即下降。多个 JVM 的 RSS 相加时，共享页面可能重复计算。单凭 RSS 增长无法判断 heap 泄漏。

本报告使用 MiB，1 MiB = 1024 × 1024 字节。

## 全量与热构建

全量构建在计时前删除本项目构建输出，执行全部模块的 `assembleDebug`。热构建保留全量产物，在同一 daemon 上再次执行，22900 个任务全部 up-to-date。

## 结果解读

本次 7.6.6 的全量与热构建耗时中位数较低。全量 RSS 峰值略高，热构建峰值略低，热后常驻中位数较高。两版 RSS 范围重叠，4 次测量不足以认定稳定的内存回归。

热构建继承全量构建后的 JVM 状态，仍会配置模块、检查任务状态并分配内存。本次 GC 日志显示，8 对热构建都将 heap 容量扩展至 6144 MiB。较高的热构建 RSS 与此现象相符，对应的 [GC 日志 CSV](data/gc.csv)和 [heap 数据 CSV](data/heap.csv)保留了原始记录。

主机原有的内存压缩与 swap 活动也会影响 RSS 观测值。

以上成绩对应数据集记录的根目录模块布局。当前源码位于 `modules/lib0000` 至 `modules/lib0999`。结论仅适用于本次合成项目、主机与 CLI 场景。CLI 配置和依赖图解析与 Android Studio Sync 的工作范围不同。
